| 字段 | 值 |

---

## 1. 为什么要清洗

本仓库不是单一生产快照，而是四类材料的混合体：

| 类型 | 典型路径 | 风险（不清洗直接入库） |
|------|----------|------------------------|
| GitHub 上游 COBOL | `02_code_assets/github_cobol/` | 版权头噪声、超长单文件、COPY 缺失 |
| 由源码反推的文档/补齐代码 | `07_derived/` | 可能含「源码没有的」测试桩接口，易被当成事实 |
| 早期虚构 CPS 资产 | `01_tech_docs/`～`04_system_metadata/`、部分 `02_code_assets` | 与 CardDemo/VAULT 实体同名冲突（如日终、制裁） |
| 故意「屎山」样本 | VIP 跳 AML、假密钥、死代码、失败 `exit 0` | 图谱/模型会学到错误业务规则与安全旁路 |

若不分层与隔离，向量检索会把冲突规则一并召回，知识图谱会出现错误的 `calls` / `implements` 边。

---

## 2. 清洗目标

1. **分层可信度**：每条记录带 `tier` / `trust` / `kind`。
2. **隔离危险与噪声**：密钥、合规旁路、死代码、未完成脚本进入隔离区，默认不进正库。
3. **双通路产出**：
   - 知识图谱：结构化三元组 `kg_triples.jsonl`
   - 向量库：带元数据的文本块 `vector_chunks.jsonl`
4. **保留溯源**：每条边/块可回溯到相对路径 `path`。
5. **禁止错误合并**：不同业务宇宙的需求编号、程序名不强行归一（见 §5）。

---

## 3. 数据分层（tier）

| tier | 含义 | 路径前缀（示例） | trust（默认） | 建议用途 |
|------|------|------------------|---------------|----------|
| **A** | 上游真实代码 | `02_code_assets/github_cobol/` | 0.95 | 图谱主实体、代码向量主库、正样本 |
| **B** | 反推/元数据（有源码依据） | `07_derived/`、`04_system_metadata/` | 0.70～0.75 | 对齐、补边；检索可进，训练需人工抽检 |
| **C** | 虚构/合成文档与代码 | `01_tech_docs/`、`03_business_rules/`、合成 JCL/COBOL 等 | 0.50～0.55 | 单独 namespace，或作对比/噪声集 |
| **隔离** | quarantine | 见 §4 | — | 默认不入库；审核后可降权进副库 |

检索过滤建议：

- 生产问答 / 规则问答：`tier in (A, B)` 且不在 quarantine。
- 仅代码理解：`tier = A` 且 `modality = code`。
- 合成场景评测：单独使用 `tier = C`，勿与 A 混训为「事实」。

## 4. 隔离规则（quarantine）

### 4.1 按文件名 / 路径命中

| 命中项 | 原因 |
|--------|------|
| `FIX_TMP_*` | 常驻「临时修复」，行为与正式设计不一致 |
| `PYMAIN.OLD`、`PYRECON#.BAK` | 废弃版本，易污染调用关系 |
| `_LANDMINES*` | 运维排雷笔记，含旁路清单，不宜当正规则 |
| `*DLQ_REPLAY_V2*` | 未完成实现 |
| `COMMON.cpy` | 冲突字段/REDEFINES 战区，语义不稳定 |
| `cps_smoke_deploy.sh` | 含硬编码假密钥 |

### 4.2 按内容正则命中（示例）

- 密钥形态：`P@ssw0rd`、`client_secret=`
- 合规旁路：`VIP skip AML`、`skip aml`、`TESTSKIPAML`
- 死代码 / 禁用：`7777-DEAD-CODE`、`DO NOT USE`、`dont submit`
- 虚假成功：Jenkins 失败仍 `exit 0` 等注释模式

命中文件写入 `08_cleaned/quarantine.jsonl`，字段含 `path`、`reason`、`preview`。

> 说明：早期「屎山」样本若用于**对抗评测**（检测模型是否拒绝旁路），应从 quarantine **显式标记**后进入副库，标签建议为 `role=adversarial`，禁止与正规则混用同一 `collection`。

## 5. 实体与编号消歧（必做）

| 冲突点 | 处理 |
|--------|------|
| `FR-001`（CPS-SWIFT）vs `FR-01`（CARD-VAULT） | **不合并**；图谱用 `(id, universe)` 或前缀 `CPS:FR-001` / `CARD:FR-01` |
| `PYMAIN` / `PYROUTE`（CPS）vs `COACTUPC` / `WIREXFR0`（Card/VAULT） | 不同系统；节点建议 `Program` + 属性 `system=CPS|CARDDEMO|VAULT|ZBANK|LEDGER` |
| 制裁：`AML*`（CPS）vs `OFACCHK0`（VAULT） | 可建抽象类型 `Screening`，实例不合并 |
| 日终：`PYRECON#`（CPS）vs `EODPROC0`（VAULT） | 同上，分系统边 |
| MQ `CARD.BILLPAY.OUT` 等 | 文档已标明为测试桩；边属性 `synthetic_interface=true`，trust 降权 |

脚本内 `entity_normalize()` 仅做大小写、去扩展名、少量别名（如 `CPS.IN`→`CPS.IN.Q`），**不会**跨 SRS 合并 FR 编号。

## 6. 分模态清洗细则

### 6.1 文档（`.md` / `.yaml` / `.json` / `.csv` / `.mmd`）

1. 统一 UTF-8，换行归一为 `\n`，去除 `\x00`。
2. 抽取结构化字段：文档编号、版本、状态、表格中的 `FR-*`。
3. 表格需求行解析为三元组：`FR-* -type→ Requirement`，`FR-* -description→ …`，描述中反引号程序名 → `implemented_by`。
4. 切块：优先按 Markdown 标题（`#`～`###`）或空行分段，块长约 **2000 字符**。
5. 明确标注「测试桩 / 反推」的段落，在元数据中保留路径，检索权重用 `trust`。

### 6.2 代码（`.cbl` / `.cob` / `.cpy` / `.jcl` / `.rpgle` / `.rex` / `.sql` / `.mqsc`）

1. 去掉大段 Apache / Amazon 版权头（保留至 `IDENTIFICATION DIVISION` / `PROGRAM-ID`）。
2. 压缩连续空行（最多保留 1 行）。
3. 抽取：
   - `PROGRAM-ID` → 程序节点
   - `CALL` / `LINK PROGRAM` / `XCTL PROGRAM` → `calls` 边
   - `WS-TRANID … VALUE 'xxxx'` → `has_tranid`
   - `DATASET` / `FILE` / `ASSIGN TO` → `uses_dataset`（trust 略降，因误匹配风险）
4. 切块：按 DIVISION / SECTION / 段名启发式切分，块长约 **3500 字符**；过滤过短块（&lt;40 字符）。
5. 单文件体量极大时（如 `COACTUPC.cbl` ~4000 行）必须切块，禁止整文件一向量。

### 6.3 扩展名与体积

- 未在白名单内的扩展名：跳过（记入 `skip_ext`）。
- 单文件 &gt; 2MB：跳过（`skip_huge`）。
- 内容过短（&lt;20 字符）：跳过（`skip_empty`）。

## 7. 产出物说明

清洗脚本运行后，在 `08_cleaned/` 生成：

| 文件 | 格式 | 说明 |
|------|------|------|
| `kg_triples.jsonl` | 每行一个 JSON | 三元组：`s,p,o,source,tier,trust` |
| `vector_chunks.jsonl` | 每行一个 JSON | 文本块：`chunk_id,text,path,modality,tier,trust,kind,retrieve_weight,…` |
| `quarantine.jsonl` | 每行一个 JSON | 被隔离文件及原因 |
| `manifest.json` | JSON | 统计、生成时间、注意事项 |
| `clean_corpus.py` | Python 3 | 可重复执行的清洗入口 |
| `数据清洗说明.md` | 本文档 | 流程与约定 |

### 7.1 三元组示例

```json
{"s":"WIREXFR0","p":"calls","o":"OFACCHK0","source":"02_code_assets/github_cobol/vault_cbs/WIREXFR0.cob","tier":"A","trust":0.95}
{"s":"FR-08","p":"implemented_by","o":"WIREXFR0","source":"07_derived/03_business_rules/SRS-CARD-VAULT.md","tier":"B","trust":0.675}
```

### 7.2 向量块元数据字段

| 字段 | 含义 |
|------|------|
| `text` | 入库嵌入的正文 |
| `path` | 相对仓库根的源路径 |
| `modality` | `code` 或 `doc` |
| `tier` / `trust` / `retrieve_weight` | 分层与检索权重 |
| `kind` | `upstream_code` / `derived_from_code` / `synthetic_doc` / … |
| `chunk_id` / `chunk_index` | 块唯一 id 与顺序 |

同一 `(s,p,o)` 多源出现时，**保留 trust 更高的一条**（`dedupe_triples`）。

## 9. 导入建议

### 9.1 知识图谱（Neo4j 等）

1. 约束：`Program.name + Program.system` 唯一；`Requirement.id + Requirement.universe` 唯一。
2. 导入 `kg_triples.jsonl`：`MERGE` 节点与关系，属性写入 `source,tier,trust`。
3. 对 `trust < 0.6` 或 `synthetic_interface=true` 的边使用虚线关系或单独 `relType`（如 `CALLS_DERIVED`）。

### 9.2 向量库（Chroma / Milvus / ES dense 等）

1. 仅嵌入 `vector_chunks.jsonl` 的 `text`。
2. `metadata` 至少写入：`path,tier,trust,modality,kind,chunk_id`。
3. 查询侧：`where tier != "C"` 或 `trust >= 0.7`；代码问答再加 `modality = "code"`。
4. **不要**把 `quarantine.jsonl` 的正文与正库同一 collection 混存。

### 9.3 训练 / 微调

| 用途 | 建议语料 |
|------|----------|
| 代码补全 / 程序理解 | 仅 tier A 代码块 |
| 需求↔实现对齐 | A 代码 + 人工确认过的 B（SRS-CARD-VAULT 等） |
| 合成支付场景 | 仅 tier C，标签 `synthetic=true` |
| 安全/合规对抗 | quarantine 中旁路样本，标签 `adversarial=true` |

禁止：把 VIP 跳过 AML、假密钥脚本当作「正确实现」正样本。
